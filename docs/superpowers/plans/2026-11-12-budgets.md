# Budgets per period Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single Planejamento plan with named budgets (income + expenses), each assigned to month ranges, with a month belonging to at most one budget, and with a tested way to revert code and data.

**Architecture:** New tables `budgets` and `budget_periods`; `income_items` and `planned_expenses` get a `budget_id`; `savings_items` is dropped. Budget and period rules live in a new `app/budgets.py` (no UI code). A startup migration in `app/database.py` moves existing rows into one budget. The Planejamento page gets a budget selector, a periods area and a month picker.

**Tech Stack:** Python 3.10+, SQLAlchemy, SQLite, NiceGUI, pytest.

**Spec:** `docs/superpowers/specs/2026-11-12-budgets-design.md`

## Global Constraints

- Months are compared as `(year, month)` tuples (`YearMonth`); an open end is `None`. This replaces the spec's integer key `year*12 + month-1` (same ordering).
- A month belongs to at most one budget. Ranges that merely touch (end Oct/2026, start Nov/2026; end Dec/2025, start Jan/2026) do not overlap.
- Open-ended range closing (`end` = month before the new start) is offered only when the new range is also open-ended and the conflicting open range starts strictly before the new start.
- Migrated budget name: `"Orçamento atual"`, created with no periods, only when `income_items` or `planned_expenses` had rows.
- Budget names: stripped, non-empty, unique case-insensitively.
- All UI text in Portuguese, matching the existing pages; money with `format_brl`; months with `month_name(m, short=True)` as `Out/2026`.
- Savings is removed entirely: model, table, crud entry, `calculate_plan` key, page section, tests.
- Every structural migration takes `_backup_before_migration()` first (existing function in `app/database.py`).
- Tests never touch the real `casa.db` (conftest sandbox). Run with `venv/bin/python -m pytest`.
- Commit messages: conventional commits, ending with the `Co-Authored-By` line required by the session's attribution reminder.
- Work on branch `feature/budgets`; nothing is pushed or merged without Rafa's go-ahead.

## Review Focus

- Ranges across a year boundary (end Dec/2025 + start Jan/2026, and closing for a Jan start giving end Dec of the previous year): must not conflict. Tested in Task 3.
- Editing a period without changing it, or only moving its end: must not conflict with itself. Tested in Task 3.
- A month with no budget (before the first range, or in a gap): lookup returns `None`; page shows "Sem orçamento". Tested in Tasks 3 and 6 (manual).
- Category delete/rename while several budgets use it: every budget's items follow the replacement. Tested in Task 1.
- Migration on an empty database, on a database with only income rows, and run twice: no stray budget, no data loss, idempotent. Tested in Task 4.

### Task 3: Periods, overlap rules and month lookup

**Files:**
- Modify: `app/budgets.py`
- Modify: `tests/test_budgets.py`

**Interfaces:**
- Consumes: `Budget`, `BudgetPeriod`, `BudgetError`.
- Produces in `app/budgets.py`:
  - `YearMonth = tuple[int, int]  # (year, month)`
  - `class PeriodConflict(BudgetError)` with attributes `conflicts: list[BudgetPeriod]` and `closable: Optional[BudgetPeriod]` (set only under the closing rule in Global Constraints)
  - `format_period(period) -> str`: `"Jan/2024 – Out/2026"` or `"Nov/2026 →"`
  - `add_period(db, budget_id: int, start: YearMonth, end: Optional[YearMonth] = None, close_conflict: bool = False) -> BudgetPeriod`
  - `update_period(db, period_id: int, start: YearMonth, end: Optional[YearMonth] = None, close_conflict: bool = False) -> BudgetPeriod`
  - `delete_period(db, period_id: int) -> bool`
  - `budget_for_month(db, month: int, year: int) -> Optional[Budget]`
  - `covered_months(budget: Budget, today: date) -> list[YearMonth]` newest first, every month of every period up to and including `today`'s month (open ends stop there; months after `today` are excluded), no duplicates

Rules: `end < start` raises `BudgetError`; any overlap with another period (any budget, including the same one) raises `PeriodConflict` whose message names the conflicting budget and `format_period`. With `close_conflict=True` and `closable` set, the closable period's end becomes the month before the new start and the new period is saved in the same commit; otherwise `close_conflict=True` changes nothing.

### Task 5: Data rollback script

**Files:**
- Create: `scripts/rollback_budgets.py`
- Create: `tests/test_rollback_budgets.py`

**Interfaces:**
- Consumes: the migration from Task 4 (its pre-migration backup is the input).
- Produces: `rollback(db_path: Path, backup_path: Path) -> dict` in the script module (importable in tests as `scripts.rollback_budgets`; add `scripts/__init__.py` if needed) and a CLI: `python scripts/rollback_budgets.py <backup.db> [--db casa.db] --confirm-app-stopped`. Returns `{"restored_income": n, "restored_expenses": n, "restored_savings": n, "safety_backup": Path}`.

Behaviour: refuses unless `--confirm-app-stopped` is passed and a `BEGIN EXCLUSIVE` on the live database succeeds (Claude's call: a flag plus a lock check, instead of detecting the server process). Writes `casa_pre_rollback_<timestamp>.db` next to the database using the SQLite backup API. Then, in one transaction: `ATTACH` the backup; drop `budget_periods`, `budgets`, `income_items`, `planned_expenses` and `savings_items` if present; recreate the last three from the `sql` stored in the backup's `sqlite_master` and copy their rows over. Every other table is untouched. Prints that budget edits made after the deploy are lost. Refuses (exit code 2, nothing changed) when the backup lacks `income_items`.
